nerdr runs the agents you already use, with their own sign-ins and
settings. An `[agents.<name>]` table in the config changes how one is
started: extra arguments, environment variables, a model, or a wrapper
such as a sandbox.

## Commands, arguments and wrappers

By default, nerdr runs each agent's command: `claude`, `opencode`,
`copilot`, `codex`, `cursor-agent`, `gemini`, `agy` or `grok`. Configure an agent
with `[agents.<name>]`:

| Setting | Effect |
|---|---|
| `command` | Replaces the command. Can include a wrapper and fixed arguments. The first word must be on your PATH. |
| `args` | Added after `command` on every launch. |
| `env` | Overrides inherited environment variables. nerdr's own variables, `NERDR_*` among them, are reserved. Agents and terminals do not inherit variables naming the agent or terminal nerdr was started from, such as `CLAUDECODE`, `TMUX` or `KITTY_WINDOW_ID`, and get `TERM_PROGRAM=nerdr`. |
| `config_model` | opencode only: its model as `provider/model`. opencode 2 dropped `--model`, so nerdr merges it into the `OPENCODE_CONFIG_CONTENT` variable, which only opencode's own server (`--standalone`, which nerdr always uses) reads. |

Without `command`, the default command is used. For example,
`[agents.claude]` with only `args` still runs `claude`. To choose a model,
put the agent's own flag in `args`, such as `--model opus` for Claude.

nerdr appends session arguments last. Wrappers must pass them through.

| Agent | Session arguments |
|---|---|
| Claude | `--session-id <id>`, `--resume <id>` or `--continue` |
| opencode | `--session <id>` or `--continue` |
| Copilot | `--session-id <id>` when supported, or `--resume=<id>` |
| Codex | `resume <id>` or `resume --last`; also `--no-daemon` when supported |
| Cursor | `--resume <id>` or `--continue` |
| Gemini | `--session-id <id>`, `--resume <id>` or `--resume latest` |
| Antigravity | `--conversation <id>` or `--continue` |
| Grok | `--session-id <id>` or `--resume <id>` |

For example, with `command = ["my-sandbox", "--", "copilot"]` and
`args = ["--allow-all"]` under `[agents.copilot]`, nerdr starts a new
tab with:

```sh
my-sandbox -- copilot --allow-all
```

Resuming adds `--resume=<id>` at the end.

Codex can share a command server across sessions. That server inherits the
first session's environment and runs outside the wrappers of later
sessions. `--no-daemon` keeps the server inside each tab's Codex process,
so it stays inside the wrapper and its reports come from the right tab.

These settings apply to new, restored, restarted and switched agents,
and to reviewers. Reviewers also get `[review.args]`. For opencode, nerdr
uses `<command> session list` to find conversations and
`<command> session export <id>` to prepare a handoff.

[Questions from the review panel](../../panel/overview/#asking-the-agent-from-the-panel) go to the
tab's agent as messages. Terminal panes and your editor run without
agent wrappers.

## Agents in a sandbox: `sandboxed`

nerdr runs as you, outside every sandbox. An agent that can reach nerdr's
hook socket could otherwise ask nerdr to do what its sandbox stops it from
doing: open a terminal pane (your shell), start an agent or a tab that is
not in a sandbox, or send such an agent a task. Set `sandboxed = true` for
an agent whose `command` puts it in a sandbox:

```toml
[agents.copilot]
command = ["my-sandbox", "--", "copilot"]
sandboxed = true
```

Such an agent:

- gets `NERDR_SANDBOXED=1`, and reports to the hook socket for agents in
  a sandbox, not the one agents outside a sandbox report to (see
  [What a sandbox must allow](#what-a-sandbox-must-allow));
- cannot open, restart or close terminal panes (`nerdr terminal`,
  `nerdr close`), nor close an agent outside a sandbox;
- can start agents, tabs (`nerdr agent`, `nerdr tab new`) and spun-off
  parts only with agents that are themselves `sandboxed`;
- can send messages to, and read the panes of, only agents started in a
  sandbox, and no terminals. A message it leaves for an agent that later
  starts outside a sandbox waits in F3 for you to approve it. Results
  from work it spun off are reported only to that agent;
- sees only its own tab in `nerdr tabs`;
- can run the plugins you allowed, but nerdr asks you before each run.
  Plugins run outside the sandbox, as you, since that is what they are
  for (see [Plugins](../plugins/#safety)).

Reviews of a sandboxed agent's work also run only in sandboxed agents,
automatic reviews and `nerdr request-review` included, and the review
picker offers only those. If the configured reviewer is not sandboxed,
nerdr picks a sandboxed agent instead, of the author's kind if need be.
If no agent can run sandboxed, no review starts. Handoffs and questions
still work: they go to you, or to an agent you pick.

The setting takes effect when the agent next starts.

A sandboxed agent cannot pretend to be one outside a sandbox. Every agent
gets its tab's secret in `NERDR_TAB`, and a process in a sandbox may be
able to read it. So on Linux and macOS, nerdr also asks the kernel which
process connects to the hook socket, and takes a request as the agent's only
if it comes from the agent itself or a process started under it, and
that started when the kernel says the agent did, so a process given the
id of an agent that has ended is not taken for it. Any
other connection is treated as sandboxed: it is restricted as above, and
refused if the tab it names is not sandboxed. The sandbox can therefore
reach nerdr's hook socket without that becoming a way out. This holds for
the hook socket alone: with the core on its own, the client socket must
stay out of reach even with `sandboxed = true` (see
[below](#what-a-sandbox-must-deny-when-the-core-runs-on-its-own)). On other systems,
nerdr cannot check the process and relies on `NERDR_TAB` alone, so a
sandboxed agent that reads another agent's secret could pretend to be
it.

The same check means that an agent outside a sandbox whose commands run
somewhere else, such as in a container or on a remote machine, can use
nerdr's commands only if you mark it `sandboxed`.

`sandboxed` does not create a sandbox; your `command` must do that. The
setting only stops nerdr from being a way out. From inside the sandbox,
check that the agent cannot reach other ways out, such as the D-Bus
session bus, a VS Code or browser socket in `/run/user/$UID`, services
on localhost, or your SSH agent: the agent gets `SSH_AUTH_SOCK` from your
environment, and only the sandbox decides whether it can use it. With
[servers](../../use/remote/), that matters more: see
[below](#with-servers-ssh-keys-and-the-ssh-agent).

nerdr runs Git in the agent's worktree outside the sandbox, so the
sandbox must keep the agent from the files of the main checkout's `.git`
that tell Git to run commands: `.git/config`, `.git/hooks`,
`.git/config.worktree` and `.git/worktrees/*/config.worktree`. To commit,
the agent needs the rest of `.git/worktrees/<name>/`, the objects and the
refs. Git reads `config.worktree` only when the repository has
`extensions.worktreeConfig` on, as `git sparse-checkout` turns it on.
While it is, nerdr does not run Git in a repository where an agent has
run in a sandbox, and tells you why, so sparse-checkout and sandboxed
agents do not go together in nerdr: see
[Security](../../reference/security/#what-nerdr-does-not-take-from-the-worktree).

nerdr also refuses host Git in repositories with sandbox history and
executable filter, textconv, external diff or merge drivers. Protected
configuration can still run a script from the agent's worktree. Globally
installed Git LFS does not block ordinary repositories, but operations
that need LFS conversion and automatic LFS uploads are refused. Use Git
inside the sandbox, or inspect the work and use your own terminal.
Protect any files included by Git configuration too. This includes files
selected by `include.path` and `includeIf.gitdir`: they must not live in an
agent-writable worktree or be replaceable by the agent. The on-branch include
refusal does not make other included files safe to leave writable.

Host Git fetch and push are also refused in repositories with sandbox
history, including SSH, HTTPS and local remotes. Authentication and signing
commands cannot be used to execute worktree scripts. Required signing
fails instead of producing an unsigned commit. Run these operations inside
the sandbox or in your own terminal after inspecting the work. Creating a
new worktree can fail when it requires a fetch; see
[Security](../../reference/security/#what-nerdr-does-not-take-from-the-worktree).

Sandbox history survives closing tabs, deleting worktrees and restarting
nerdr. Imported sandboxed work keeps that history even if the destination
agent never starts. If agent settings change while a launch is being
prepared, nerdr refuses that pending launch; restart the agent to use the
new settings.

Text that an agent outside a sandbox reads from one inside, such as code
to review, a handoff or a review, was still written by the sandboxed
agent and can contain instructions. It is safest to run every agent in a
sandbox, or nerdr itself in one.

## Setting nerdr up for a sandbox

This section gathers what to set in nerdr and what to weigh. It holds for
any sandbox; the sections after it say what the sandbox itself must allow
and deny.

### What to set

| Setting | Set it to | Why |
|---|---|---|
| `sandboxed` | `true` for every agent whose `command` is a sandbox | nerdr then holds the agent back on the hook socket, and checks its sandbox before each start. |
| `command` | The sandbox, then the agent's own program as a word of its own | The check runs nerdr where that word is. For a wrapper that picks the agent some other way, by an option or by default, set `check_command`. |
| `check_command` | Only for such a wrapper: a command that runs the program after it in the agent's sandbox | The check runs through it instead. See [the check](#checking-a-wrapper-that-picks-the-agent-itself). |
| `install` | `"worktree"` | nerdr's skills and plugins go in each tab's folder, where only that tab's agent can change them. See [below](#where-nerdr-installs-install). |
| `data_dir` | A folder in the worktree, such as `".nerdr"` | Each tab's agent writes only its own notes, reviews and handoffs. See [below](#where-the-records-are-kept-data_dir). |

```toml
install = "worktree"
data_dir = ".nerdr"

[agents.copilot]
command = ["my-sandbox", "--", "copilot"]
sandboxed = true
```

### Every agent in a sandbox, or only some

Run every agent in a sandbox if you can. What nerdr does for a sandboxed
agent holds either way, but an agent outside a sandbox still reads what
one inside wrote: the code it reviews, a handoff it takes over, a message
you approve in F3, files in folders both can write. Text there can hold
instructions, and the agent outside can do anything you can. With every
agent in a sandbox, there is no such agent to steer.

Terminal panes and your editor always run as you, with no wrapper, in a
worktree the agent has written. What your shell or editor loads from a
folder by itself, such as an environment file or workspace settings, is
then the agent's to write.

### Letting the agent reach nerdr

The agent reaches nerdr through the hook socket. You choose whether its
sandbox lets it.

| | Sandbox allows the socket | Sandbox denies it |
|---|---|---|
| Status of the agent | From its hooks: exact | Read off the screen: can be wrong between steps |
| Code review by another agent, spinoff, handoff, messages between agents, plugins | Work, held back as [above](#agents-in-a-sandbox-sandboxed) | Do not work. nerdr warns you once that no reports arrive |
| Explanations and walkthroughs | Work | Work, when the sandbox can run `$NERDR_BIN` or the agent writes the files in `data_dir` itself |
| What the agent can ask of nerdr | What a sandboxed agent may | Nothing |

With the socket allowed, two things are yours to see to:

- **Allow connecting, and no more.** A rule that also lets the agent
  remove the socket's file, or listen at its path, lets it put a socket of
  its own there. The nerdr commands of the other agents in a sandbox
  would then talk to that one, which could answer them in nerdr's place
  and see what they send. Agents outside a sandbox use a socket of their
  own that a sandbox cannot reach, so they are not among them. nerdr
  looks at the socket every two seconds: when it is gone or replaced,
  nerdr listens there again and tells you, but what was asked in
  between went to the other socket.
- **Read what you say yes to.** A plugin runs outside the sandbox, as
  you, with the parameters the agent gave it. nerdr asks before each run
  a sandboxed agent starts, and that question is the guard.

### Where nerdr installs: `install`

| | `"worktree"` | `"home"` |
|---|---|---|
| Skills are found | In nerdr's tabs | By the agents outside nerdr too |
| Who can change them | The tab's own agent, for itself | Any agent whose sandbox lets it write the agent's folder in your home folder, for every agent |
| Files in the worktree | Yes, kept out of git | Only Copilot's plugin, for a copilot in a sandbox |

Neither setting keeps an agent from writing the agents' folders in your
home folder: with `"worktree"` nerdr only puts nothing of its own there.
The agents load what is in them all the same, so the sandbox should deny
writing them. With `"home"`, nerdr's check tells you when it does not.
See [Where skills are installed](../../panel/skills/#where-skills-are-installed).

### Where the records are kept: `data_dir`

| | In the worktree (`".nerdr"`) | Empty: the repository's `.git/nerdr` |
|---|---|---|
| Who can write a tab's records | Its own agent | Every agent with a worktree of the repository |
| When the worktree is deleted | Deleted with it | Kept |
| Shared between the repository's tabs | No | Yes |

With the shared folder, an agent in one tab can write a handoff or a
review that an agent in another tab reads as its own.

### What nerdr no longer does in the repository

Once an agent has run in a sandbox in a repository, nerdr treats what is
in it as the agent's, and stops doing as you what the agent could turn
into running its code. This stays so after the tab is closed, until you
have nerdr forget it. The Git hooks and the code review follow the tab
the agent ran in; the rest holds for the whole repository.

| nerdr | Where an agent has run in a sandbox |
|---|---|
| Fetch and push | Refused, but for the fetch a new tab needs. Push from inside the sandbox, which then needs the network and your credentials, or from your own terminal once you have read the change |
| Git hooks on commit and push | Not run. Commit in your own terminal to have them |
| `.nerdr.toml` setup | Skipped when `copy` has any pattern. Run it in the sandbox, or yourself |
| Signed commits | Fail when signing is required, instead of being made unsigned |
| Git LFS | Operations that need conversion fail |
| Filter, diff and merge drivers that run a program | All host Git is refused while one is configured |
| `git sparse-checkout` | All host Git is refused while `extensions.worktreeConfig` is on |
| Code review of the agent's work | Runs only in agents that are themselves sandboxed |

See [Security](../../reference/security/#what-nerdr-does-not-take-from-the-worktree)
for each, and for how to have nerdr forget a repository's sandbox history.

### What nerdr does not see to

- **Other ways out of the sandbox.** nerdr checks its own socket, files
  and folders. The D-Bus session bus, sockets of other programs, services
  on localhost and your credentials are the sandbox's to deny.
- **Your SSH keys and SSH agent**, which reach nerdr on your
  [servers](#with-servers-ssh-keys-and-the-ssh-agent).
- **What the sandbox gives the agent on purpose**, such as a token to
  push with. The agent can use it for anything the token allows.

## Other agents

Add a named section with `command` to offer another agent in the picker:

```toml
[agents.my-agent]
command = ["my-agent"]
resume_args = ["--continue"]  # used on resume; omitted means a new conversation
detect = "amp"                # screen rules to use; defaults to the agent's name
```

`detect` selects the screen rules. nerdr has them for amp, cline,
devin, droid, hermes, kilo, kimi, kiro, letta, maki, muse, pi,
qodercli and qwen besides its own agents. Without matching rules, the status is unknown, but the tab
still works. `detect` also works for built-in agents, such as one behind
a wrapper that changes its screen.

nerdr does not know where custom agents store conversations, so it
resumes one with `resume_args`. When you switch away from
such an agent, nerdr cannot read its conversation, so it relies on a
handoff the agent writes.

## What a sandbox must allow

Each agent receives `NERDR_BIN` (the nerdr executable) and
`NERDR_DATA_DIR` (the data location). `NERDR_BIN` is the path nerdr was
started from, such as `/opt/homebrew/bin/nerdr`, rather than the file a
link there points to, so an agent that keeps running while nerdr is
updated still finds it. Skills use
`"${NERDR_BIN:-nerdr}" why add …`. This reads `NERDR_DATA_DIR` without
needing access to the config file.

For a sandbox restricted to the worktree, use:

```toml
install = "worktree"
data_dir = ".nerdr"
```

Allow the sandbox to run `NERDR_BIN`, or put nerdr on its PATH. If that
is unavailable, skills instruct the agent to append JSON lines directly
to the files in that folder.

Commands such as `request-review`, `post-review`, `spinoff` and `handoff`
need more. Each call, from a skill or from an agent's hooks, starts a
new `nerdr` process that passes the request on to the nerdr running the
tab, and finds it only through the `NERDR_*` variables and its socket.
The sandbox must:

- pass the `NERDR_*` variables through, `NERDR_SOCKET` and `NERDR_TAB`
  among them;
- allow running `$NERDR_BIN`, and the file it links to when it is a
  link, as Homebrew's is;
- allow connecting to the socket at `$NERDR_SOCKET`. For an agent in a
  sandbox it is always `~/.local/state/nerdr/nerdr.sock`
  (`$XDG_STATE_HOME/nerdr/nerdr.sock` when that is set), whatever folder
  nerdr starts in, so the rule can name that one path. Connecting is all
  it needs: do not let the agent remove the file or listen at the path
  (see [Letting the agent reach nerdr](#letting-the-agent-reach-nerdr)).

nerdr listens on two hook sockets. That one is for the agents it starts
in a sandbox, those whose kind is `sandboxed`. The agents it starts
outside one get another, in the client socket's folder (see
[below](#what-a-sandbox-must-deny-when-the-core-runs-on-its-own)),
which a sandbox must deny anyway: an agent in a sandbox that may replace
its socket then reaches only other agents in a sandbox, never one that
can do anything you can. Each agent is given its socket when it starts;
one that was running when nerdr was updated keeps the one it was given.

One nerdr has that socket at a time. A second instance started in
another folder notifies you and listens on its own socket in the same
directory, `nerdr-<id>.sock`. If a sandbox only allows access to
`nerdr.sock`, allow it to connect to all sockets in that directory so
both instances work. The sockets nerdr makes in that directory are all
hook sockets for agents in a sandbox: the client socket and the hook
socket for agents outside one are elsewhere, and the holder's has no
path (see [below](#what-a-sandbox-must-deny-when-the-core-runs-on-its-own)),
so allowing connections to them reaches none of those.

Agent commands never write to `~/.local/state/nerdr`: connecting to the
socket is all the sandbox needs there. Never let a sandbox write to
`~/.local/state/nerdr` or `~/.config/nerdr` — an agent with write access
could create or approve plugins for itself (see
[Plugins](../plugins/#safety) and [Security](../../reference/security/)).
For read access:

- `nerdr usage` reads `~/.local/state/nerdr/sessions/claude-limits.json`
  for the Claude plan's limits and `~/.codex/sessions` for Codex's
  (without them, it reports the limits as unknown). Allow only
  `claude-limits.json`, not the rest of `sessions/`.
- `nerdr plugin` reads `~/.config/nerdr/plugins`.
- `nerdr search` reads conversation logs in `~/.claude/projects` and
  `~/.codex/sessions`.

When something is missing, the
command says which of these it is, and the skills tell the agent to show
the user that message rather than try another nerdr.

nerdr notices too. The integrations for Claude, Copilot and Codex report
to nerdr through the same executable and socket while they work. If a
sandboxed agent finishes a turn without any reports reaching nerdr,
nerdr warns you once and shows the executable and socket paths the
sandbox must allow. If a reviewer stops this way, its review status line
reports that its sandbox blocked it from reaching nerdr.

## What a sandbox must deny when the core runs on its own

nerdr runs the agents in a process of its own, the core, under a holder
that starts each program (see
[How it works](../../reference/how-it-works/#the-core-and-the-holder)),
and the nerdr you see connects to it. With `NERDR_HOLDER=0` nerdr runs
them itself, the way it did before the core, they end with it, and of
this section only the client socket's folder applies: the hook socket of
the agents outside a sandbox is there too.
Closing the window, or choosing **Close** when you leave nerdr, leaves
the agents, terminals and plugin runs working with no one watching; start
nerdr in the same folder to connect again. **Quit** stops them. While no
nerdr is connected, nothing is approved for you: a `.nerdr.toml` setup
that needs your approval waits until you connect, and a plugin run that
needs it does not run when its time to be answered runs out. What you
allowed before, such as an approved setup or a plugin that is not asked
about at each run, still runs.

This adds two things a sandboxed agent must not reach. Everything above
still applies. A sandbox that was enough for nerdr before the core, one
that lets the agent read and connect to anything in your home folder or
in `$XDG_RUNTIME_DIR`, is not: it must now deny them too. When the check
below finds the agent can reach them, or cannot establish whether it can,
nerdr does not start it.

- **The client socket's folder.** A client can do anything you can,
  approvals included. Its socket and the key to it, and the hook socket
  of the agents outside a sandbox, are in
  `$XDG_RUNTIME_DIR/nerdr` when `XDG_RUNTIME_DIR` is set; without it, in
  `~/.cache/nerdr/run` on Linux and `~/Library/Application Support/nerdr/run`
  on macOS; never under `~/.local/state/nerdr`. The sandbox must deny
  connecting to the socket and reading the key there, not only writing
  to the folder (better still, it denies the whole folder): a sandbox that lets the agent
  read and connect to anything in your home folder is enough without the
  core, but not with it. nerdr also refuses a client run by one of its
  own programs, but a process that has left the agent's process tree
  gets past that.
- **nerdr's processes.** nerdr's core and the holder, the process that
  starts every agent and terminal, talk over a socket with no path. A
  process that may trace them (`ptrace`) or take their descriptors
  (`pidfd_getfd`) could still take it. On Linux, Yama's
  `kernel.yama.ptrace_scope` of 1 or more stops that for processes the
  holder started that lack `CAP_SYS_PTRACE`; at 0 only the sandbox stops
  it, with a PID namespace of its own or by denying those calls.

An agent, terminal or plugin started while you are connected builds on
the environment of the nerdr you connected with, as it would without the
core: `PATH`, `SSH_AUTH_SOCK`, `DBUS_SESSION_BUS_ADDRESS` and the rest
come from your terminal, not from the one that first started the core,
with nerdr's own variables and the agent's `env` added. One started with
no nerdr connected gets the environment of the last one that connected to
this core; before any has, as when the core has just started again, the
one the core started with. A program keeps the environment it started
with. What the agent can reach of it is up to its sandbox. On a server,
nerdr on your laptop sends no environment: the programs there get the
server's [login environment](../../use/remote/#the-agents-environment-on-a-server).

When a `sandboxed` agent starts, nerdr first checks from inside its
sandbox: it runs its own executable through the agent's `command`, in
place of the agent, with the agent's environment and folder. Each of
these but `folder` that gets through counts as reaching nerdr:

| The check reports | What it tries | It gets through when |
| --- | --- | --- |
| `folder` | Look up the client socket's file (`lstat`), and list the client socket's folder | The socket's file can be looked up, or the listing shows it. Looking up a file needs only its metadata: a sandbox that denies reading the folder's files but allows reading metadata everywhere, as many macOS profiles do, still lets this through. This alone does not keep the agent from starting: nerdr starts it, and notes the folder in the [history (F6)](../../panel/history/) and the core's log, not in the bar, since what is in the folder is no way in without connecting to the socket or reading the key |
| `socket` | Connect to the client socket | The connection is made. On macOS, connecting to a Unix socket is a network rule in a sandbox profile, not a file rule |
| `key` | Read the client socket's key file | It reads anything from it |
| `/proc <pid>` | Open a socket of the core's or holder's through `/proc/<pid>/fd` (Linux) | One opens |
| `pidfd_getfd <pid>` | Take a descriptor of the core's or holder's with `pidfd_getfd` (Linux) | One is taken |
| `ptrace <pid>` | Trace the core or holder (Linux) | It may |

The last three are tried only on Linux, and only when the check runs in
the core's PID namespace: in one of its own, the process ids mean other
processes. On macOS they are not tried.

If any of the others gets through, nerdr does not start the agent. The tab shows
why in full until you start the agent again: what the check reached, and
the paths it tried, the client socket's folder, the socket and the key,
as nerdr has them, with the folder's real path too when a link leads
there. Those paths are the ones the sandbox's rule must deny. nerdr also
writes it to the core's log in `~/.local/state/nerdr/`, on a line that
starts `sandbox check:`.

The check also tries to write where the agent must not be able to:
`~/.config/nerdr`, `~/.local/state/nerdr` and its `tmp` folder by itself
(nerdr checks a new worktree's files out from a store there), the
`.git/config` and `.git/hooks` of the main checkouts of the tab's
repositories, and the folder the other tabs' worktrees are in. An agent that can write another
tab's worktree can change the code that tab's agent and setup command
run, outside its own sandbox. A folder counts as writable when the
check can make a file in it (`.nerdr-sandbox-check-…`, removed at once);
a file, when it can be opened to append to, with nothing written. One
that is not there is not tried. When any of them can be written, nerdr
refuses to start the agent and its tab names them: tighten the
sandbox so it lets the agent write its own worktree, and of the main
checkout's `.git` only what a commit needs.

With `install = "home"`, the check also tries to write where nerdr puts
its skills, plugins and hooks for every agent: the skills folders in your
home folder (`~/.claude/skills`, `~/.agents/skills`, …), opencode's
`~/.config/opencode/plugins`, agy's `~/.gemini/config/hooks.json` and
grok's `~/.grok/hooks/nerdr.json`, each file with its folder. A folder
that is not there is not tried, nor made. Many sandboxes let their agent
write its own folders in the home folder, so this does not stop the
agent: nerdr starts it and shows a notice naming them, since a sandboxed
agent that can write them can change what agents outside a sandbox load
from there. The notice comes once for each kind of agent, and again
when what it can write has changed, not at every start. Set
`install = "worktree"`, or have the sandbox deny writing
them. Copilot's plugin is not among them: nerdr gives each copilot its
own (see [Where skills are installed](../../panel/skills/#where-skills-are-installed)).

The check runs before every sandboxed launch, including with
`NERDR_HOLDER=0`, using that launch's folder and environment. Results are not cached: a wrapper's policy can change
with its files, configuration, environment or working directory. After
correcting the sandbox, restart the agent to have it checked again.

nerdr puts the check where the agent's program is in `command`: the last
word named as the agent is (`claude`, `codex`, `cursor-agent`, …, or the
section's name for an agent nerdr does not know). If none is, as with a
single script that starts the sandbox and the agent, or the sandbox
cannot run `$NERDR_BIN`, nerdr refuses to start the agent, and its tab
says it could not check, and why. Configure a wrapper that can run both the agent and the check
inside the same sandbox, or set `check_command` (below).

An agent's built-in sandbox for tool commands alone cannot be verified
by this external check. Marking a plain `codex` command as `sandboxed`
does not put the check inside Codex's tool sandbox: the probe runs outside
it and is refused if it can reach the client socket. Use an external
sandbox wrapper that also confines the probe.

The check catches a sandbox set up wrong.
It does not stop an agent that gets out some other way, and it says
nothing about D-Bus, sockets in `/run/user/$UID`, services on localhost,
your SSH agent or other credentials.

### Checking a wrapper that picks the agent itself

Some wrappers do not take the agent's program as a word of its own: they
start an agent by default, or pick it with an option such as
`--agent opencode`. nerdr then finds no place for the check in
`command`, or puts itself where the wrapper expects an agent's name, and
refuses to start the agent. If the wrapper can run any program in a
sandbox, give that command as `check_command`. nerdr adds its own program
and the check's arguments at the end and runs that in place of `command`,
with the agent's folder and environment:

```toml
[agents.opencode]
command = ["my-sandbox", "--agent", "opencode", "--"]
check_command = ["my-sandbox", "exec", "--"]
sandboxed = true
```

The check then tries the sandbox `check_command` gives, not necessarily
the one the agent gets. If the wrapper gives other programs a policy of
their own, wider or narrower than the agent's, the check says nothing
certain about the agent's: the agent may reach what the check could
not, or nerdr may refuse an agent whose own sandbox is tight enough.
Use `check_command` only with a command whose sandbox is the agent's, or
denies the same as it at least, and test that yourself. Everything else
holds as without it: if the check does not answer, or reaches what it
must not, nerdr does not start the agent.

## With servers: SSH keys and the SSH agent

When nerdr shows [agents on other machines](../../use/remote/), it
reaches them with `ssh box nerdr bridge …`. Anything on your laptop that
can use your SSH keys can do the same, and drive the agents on that
server as you, approvals included. So a sandbox on your laptop must also
deny:

- `~/.ssh`, your keys and `~/.ssh/config` with them, and
- your SSH agent: the socket `SSH_AUTH_SOCK` names, which the agent
  inherits from your environment.

nerdr does not check this: its sandbox check does not look at `~/.ssh`
or the SSH agent. An agent outside a sandbox can reach your servers
anyway, as you can. nerdr started by an agent in a tab does not connect
to other machines, to catch mistakes, but that is no guard.

On the server, the rules above apply as they are. nerdr's core there
refuses a bridge started by one of its own agents, and the bridge leaves
`SSH_AUTH_SOCK` out of the agents' environment, so an SSH agent you
forward to the server does not reach them. nerdr itself connects with
`ForwardAgent=no`.
